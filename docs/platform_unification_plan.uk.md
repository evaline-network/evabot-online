# 🌐 EvaLine Platform Unification — Єдина платформа з незалежних вузлів

**Версія:** 0.1.0 (концепт-план)
**Дата:** 6 вересня 2026 р.
**Автор:** EvaBot Engineering Team (аудит + архітектура)
**Статус:** План на узгодження → реалізація після ревʼю

---

## 1. Мета

Звʼязати **всі проєкти та сервіси екосистеми EvaLine** в єдину платформу зі спільною
навігацією, єдиним дизайн-стандартом і спільним бекендом, **при цьому кожен вузол
залишається повністю незалежним**: може жити, деплоїтися і працювати сам по собі,
а при відмові інших вузлів не втрачає працездатність.

## 3. Цільова архітектура: «Єдина платформа = Mesh незалежних вузлів»

```
                        ┌──────────────────────────────────────────┐
                        │           CLIENT / BROWSER               │
                        └──────────────────┬───────────────────────┘
                                           │ HTTPS :443
                    ┌──────────────────────┼──────────────────────┐
                    ▼                      ▼                      ▼
             evabot.online          evaline.network        evaline.online
             evaline.website        (і майбутні вузли)
                    │                      │                      │
                    └──────────┬───────────┴───────────┬──────────┘
                               ▼                       │
                 ┌─────────────────────┐               │
                 │  EvaFace (Caddy)    │               │
                 │  спільний CDN/статик│   /api/* через Tailscale
                 │  + спільний bundle  │               │
                 └─────────┬───────────┘               │
                           ▼                           │
                 ┌─────────────────────┐               │
                 │  EvaBrain (Brain)   │◄──────────────┘
                 │  evabot-brain:3000  │
                 │  omniroute:20128    │
                 │  antigravity:9090   │
                 │  n8n:5678           │
                 └─────────────────────┘
```

### 3.1 Ключовий принцип

1. **Спільний двигун (bundle)** — єдиний JS-файл із термінальним TUI-двигуном,
   темою, навігацією та віджетами. Збирається один раз, роздається як статика.
2. **Домен-специфічний конфіг** — маленький JSON/JS на кожен вузол:
   `{ siteId, title, section, modules: [...], apiBase, theme }`.
   Вузол обирає і монтує лише потрібні модулі. **Сайт працює без інших.**
3. **Спільний бекенд** — один evabot-brain :3000 на Brain, проксіюється на всі домени.
   Контракти API описані окремо (див. п.5).
4. **Mesh-навігація** — спільний навігаційний компонент, але кожна сторінка показує
   graceful fallback (статус OFFLINE), коли інші вузли недоступні, не ламаючись.

## 5. Єдиний контракт API (спільний бекенд на Brain)

Усі домени спілкуються з `evabot-brain:3000` через відносні шляхи `/api/*`
(проксіюється Caddy). Це **не потребує** домен-специфічних ключів і спрощує незалежність.

| Метод | Шлях | Призначення |
| :--- | :--- | :--- |
| GET | `/api/health` | Статус бекенду + кластера (Brain/Face/WireGuard) |
| GET | `/api/nodes` | Живий статус усіх вузлів платформи *(нове)* |
| POST | `/api/chat` | Унарна генерація чату |
| POST | `/api/chat/stream` | SSE-стрімінг |
| POST | `/api/consilium` | Consilium (solo/broadcast/dialogue/consilium) |
| GET | `/api/models` | Каталог моделей (36 шт., USD/EUR) |
| GET | `/api/roles` | Корпоративні ролі |
| GET | `/api/diagnostics/boot` | Діагностика завантаження |
| GET | `/api/worklog` | Хроніка (JSON) |
| GET | `/api/openapi.json` | Специфікація API *(нове)* |

## 6. Принципи, що гарантують незалежність

1. **Статика відділена від даних.** Кожен HTML/JS працює без бекенду:
   метрики й навігація показують «OFFLINE», але сторінка рендериться.
2. **Спільний код — одне джерело істини; контент — локальний.** Домен може
   мати власну секцію/модуль, не впливаючи на інші.
3. **Проксіювання `/api/*` глобально-опціональне.** Блок Caddy винесено в
   спільний імпорт; додавання нового домену — один рядок + одна папка.
4. **Mesh-навігація не є критичним шляхом.** Вона лише інформує про доступність
   сусідів, не блокуючи роботу поточного вузла.

## 7. Ризики та рішення

| Ризик | Рішення |
| :--- | :--- |
| Дублювання коду в 4 HTML → розсинхрон | Єдиний `bundle.js` + конфіг вузла |
| e2-micro не тягне багато статики | CDN-логіка: статика кешується, bundle один |
| Відмова однієї служби Brain | Graceful fallback, статуси в `/api/nodes` |
| Багато доменів у Caddyfile → дублювання | Спільний `import common_api` + `import common_root` |

---

## 8. Підсумок (що дасть реалізація)

- **Єдина платформа:** спільний дизайн, навігація, бекенд, каталог моделей.
- **Незалежні вузли:** кожен домен самодостатній і працює при відмові інших.
- **Мінімум дублювання:** один bundle, один сервер, один формат конфігу.
- **Масштабованість:** новий домен = папка + конфіг + рядок у Caddy.
